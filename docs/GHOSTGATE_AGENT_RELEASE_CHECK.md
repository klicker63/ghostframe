# GhostGate Agent Release Check

## Offer summary

GhostGate Agent Release Check is a fixed-scope, independent technical release assessment for one exact AI-agent version and one tested configuration. It answers:

> Can this exact version of this AI agent be trusted with these tools, permissions, data, and actions before release?

GhostGate evaluates the agreed build against hostile, misuse, permission-boundary, and behavioral scenarios. GhostFrame delivers a human-reviewed release verdict and a version-bound evidence package. The offer is an entry path into GhostGate, not a guarantee of safety, a certification, or a general AI consulting engagement.

## Ideal buyer

The ideal buyer is an AI-agent vendor, security lead, platform team, engineering leader, or governance owner that:

- is preparing a specific agent version for release;
- must answer an enterprise customer or procurement security review;
- needs independent evidence about tool use, permissions, and multi-step behavior;
- can provide a stable build plus a usable sandbox, test endpoint, supported adapter, or execution package; and
- wants a bounded release decision before investing in broader multi-agent qualification.

The fixed package is not a fit when the buyer needs open-ended consulting, multiple materially different versions, production monitoring, compliance certification, or broad deployment integration.

## Scope

- One AI agent
- One exact agent version or immutable build
- One test environment or supported adapter
- One tool and permission configuration
- One policy baseline
- Up to 20 agreed hostile, misuse, permission-boundary, and behavioral scenarios
- Behavioral and multi-step action-chain analysis
- Pass, Conditional Pass, or Block release verdict
- One remediation retest of the same version and agreed scope

The assessed subject is the exact combination of build, model, system instructions, orchestration, tools, permissions, retrieval sources, memory behavior, policy baseline, and deployment configuration documented at kickoff.

## Deliverables

- Agent Trust Report
- Pass, Conditional Pass, or Block release verdict
- Permission Envelope in JSON and YAML
- Findings with behavioral evidence and recommended restrictions
- Scenario and coverage summary
- Action timeline
- Signed version-bound attestation
- Downloadable evidence bundle
- One remediation retest of the same version and agreed scope

The verdict definitions are:

- **Pass:** The tested version completed the agreed assessment without release-blocking findings under the tested configuration.
- **Conditional Pass:** The version may proceed only with documented restrictions, approvals, or Permission Envelope controls.
- **Block:** The tested version demonstrated behavior or access paths that should prevent release until remediated and retested.

Every verdict applies only to the assessed version, environment, configuration, policy baseline, and agreed scope.

## Process

1. Buyer submits the public scope-review form without secrets or credentials.
2. GhostFrame confirms suitability, fixed-scope fit, and test readiness.
3. Buyer supplies the post-form technical intake through an agreed secure method.
4. Parties confirm the immutable build, scenario scope, policy baseline, and access boundary.
5. Kickoff occurs and the buyer pays the initial 50 percent.
6. GhostGate runs the agreed assessment.
7. GhostFrame performs human review and delivers findings plus release evidence.
8. One same-version, same-scope remediation retest remains available under the retest policy.

The seven-business-day target begins only after GhostFrame has received a complete intake package, confirmed the scope, and validated usable test access. Form submission alone does not start delivery or create a binding engagement.

## Buyer requirements

The buyer must provide:

- agent name and intended purpose;
- exact version or immutable build identifier;
- models and orchestration components;
- system instructions or a sufficient test representation;
- available tools and operations;
- permission and credential boundaries;
- expected and prohibited behaviors;
- a sandbox, test endpoint, supported adapter, or execution package;
- a technical point of contact; and
- known concerns or prior incidents relevant to the assessment.

The public form must never receive passwords, API keys, tokens, customer records, proprietary prompts, production credentials, private repository access, or other sensitive material. Any later access method must be agreed separately, minimized, scoped, and suitable for testing.

## Material-change policy

Release evidence and the signed attestation are bound to the assessed version and configuration. A material change invalidates or requires renewal of that evidence.

Material changes include changes to:

- the model or model version;
- system instructions or material prompt behavior;
- tool access or available operations;
- permission or credential boundaries;
- agent code;
- orchestration components or control flow;
- retrieval sources;
- memory behavior;
- the policy baseline; or
- deployment configuration.

GhostFrame determines during scope review whether a change remains within the original retest boundary or requires a new Release Check.

## Retest policy

The package includes one remediation retest of the same agent version and agreed scope. The retest verifies whether agreed remediation or restrictions resolve the documented finding paths.

The included retest does not cover a materially different version, new tools, expanded permissions, new policies, additional environments, or additional scenario coverage. Those changes require a scope change or a new assessment.

## Internal sales notes

- Lead with the release decision, not with platform breadth.
- Ask which exact build is under review, what it can access, and what decision the buyer must make.
- Confirm that a usable, scoped test method exists before discussing a kickoff date.
- Do not request credentials or sensitive technical assets in email or the public form.
- Use the public evidence room to show format and reviewability, not to imply the sample represents customer production validation.
- Do not position Pass as an unrestricted release recommendation. Restrictions may still be appropriate.
- If the buyer names multiple agents, materially different versions, multiple workspaces, or operational integration, present the private pilot rather than stretching the Release Check.
- If the buyer asks for certification, legal conclusions, production interception, monitoring, SSO, hosting, or deployment automation, state that those are outside the fixed offer.
- Treat the requested assessment date as planning input only until intake readiness is confirmed.
